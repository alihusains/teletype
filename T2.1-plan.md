## 1. The question: aliases on `DictionaryWord`, or a separate learned store?

**Decision: on the word (EW model), not a separate store.**

A learned correction `(mishearing -> correct spelling)` is a property *of a word*,
not an independent entity. The user-facing unit is one word with a list of
sound-alikes; a second "learned corrections" table would require join logic,
conflict resolution (which word does a mishearing belong to?), and a third UI
surface. It also breaks the one-file-per-concept storage Teletype uses
(`dictionary.json`, `profile.json`, ...).

### How EnviousWispr implements it (verified against the reference tree)

EW's answer is: **one word store, provenance on the word, a judge in front of
the write, an undo pill after it.**

`CustomWord` (`Sources/EnviousWisprCore/CustomWord.swift`):

```swift
public struct CustomWord: Codable {
  public let id: UUID
  public var canonical: String        // the correct spelling, e.g. "Saoirse"
  public var aliases: [String]        // all sound-alikes (user-typed or learned)
  public var category: WordCategory   // general | person | brand | acronym | domain
  public var priority: Int
  public var forceReplace: Bool
  public var caseSensitive: Bool
  public let source: WordSource       // runtime-only: builtin | user | pack (NOT persisted)
  public var frequencyUsed: Int       // times the corrector replaced into this word
  public var lastUsed: Date?
  public var minSimilarityOverride: Double?   // per-word fuzzy strictness
  public var learnedAliases: [String] // subset of aliases the APP learned from edits
  public var learnedAt: Date?         // non-nil => the whole word was auto-created
  public var isAutoLearned: Bool { learnedAt != nil || !learnedAliases.isEmpty }
}
```

Key properties of the EW design:

1. **`aliases` is the correction map.** A mishearing is an alias of the
   canonical. Correction = exact-alias lookup first, fuzzy match second
   (`WordCorrector`), applied pre-polish.
2. **Provenance, not a separate table.** `learnedAliases` marks which aliases
   were auto-learned (UI sparkle + "Auto-learned" filter); `learnedAt` marks a
   word the app created. A user-typed alias and a learned alias are the same
   shape, so the corrector does not care which produced it.
3. **`source` is runtime-only** (excluded from `CodingKeys`): anything decoded
   from disk is `.user`; builtins and pack terms are tagged in memory. This is
   what enforces the lane law (pack terms reach the corrector only, never the
   polish prompt) as a compile-time fact (see `VocabularyLanes.swift`:
   `CorrectorVocabulary` vs `PolishVocabulary` vs `SnippetVocabulary`).
4. **The write is judged, not blind.** `RulesCorrectionJudge` (deterministic,
   all macOS versions) or `CoreMLCorrectionJudge` (~305 MB on-device model,
   macOS 26+) answers one question: is this edit a *vocabulary correction*
   (a mishearing fixed) and not a rewording/grammar/punctuation edit? Only
   `correctionAndSafe` results are saved. `ObservedCorrectionWatcher` watches
   the pasted text via accessibility for up to 60 s, with generation /
   revision / cancelled guards so stale judge answers are dropped.
5. **Save at once, undo for 3 s.** `LearnedCorrectionCoordinator` owns the one
   vocabulary write. No accept/reject card, no pending queue (EW removed the
   ask-first flow on 2026-09-21: "no accept, no reject. It just auto accepts
   with an undo button"). The Undo record is in-memory only (exact pre-save and
   post-save snapshots); a crash between save and pill loses the undo chance,
   never the word. Refusals are typed: `target_gone`, `alias_owned_elsewhere`,
   `vocabulary_write_failed`.
6. **User words beat packs, packs beat nothing.** `proposalTarget` resolves:
   existing user word (append alias) > pack term (create user *override* of
   the pack term) > new word. Pack terms are length-gated in the corrector:
   they only match after every non-pack pass misses, so user/builtin words
   always win.
7. **Builtins have tombstones.** Deleting a builtin is recorded so app updates
   do not resurrect it; a learn that targets a deleted builtin restores it as
   a user-owned override, and Undo re-deletes it.

EW's builtins already ship with aliases (`"Git hub"` aliases: `"git hub"`,
`"get hub"`; `"iOS"`: `"I OS"`, `"eye OS"`), and the vocabulary packs
(`Resources/Packs/{tech,brands,legal,medical,names}.json`, ~31 KB total) are
just `{canonical: [aliases]}` maps mined from ASR mishearing data.

### What Teletype gets from this

- `DictionaryWord` grows `aliases`, `learned_aliases`, `learned_at`,
  `frequency_used`, `last_used`, `category`. Purely additive JSON (serde
  `#[serde(default)]`), forward/backward compatible like EW's schema.
- The existing `fuzzy: bool` stays (Teletype's builtins are exact-only; EW
  achieves the same with per-source matching order, but our flag is simpler
  and already tested).
- No new file, no new table, no join. `dictionary.json` remains the single
  word store; packs are read-only resources layered under it; the
  personalization `profile.json` keeps *phrase-level* preferences (greetings,
  sign-offs) where it already lives.

**What we deliberately do NOT copy from EW:**

- The accessibility text-watch of the pasted document (large, macOS-only,
  needs the same permission chain). Teletype Phase 2 uses the *history*
  path: the user re-edits in the History screen / re-dicts, and the app diffs
  AI output vs final text. Same judge, cheaper trigger.
- The 305 MB CoreML judge model. Teletype starts with the deterministic
  rules arm only (port of `RulesCorrectionJudge` semantics). The model arm is
  a later option, on-demand download, never blocking.
- Telemetry (EW fires `learn_added` / `learn_undo_shown` / ...; Teletype has
  zero telemetry by non-negotiable). We log structured local lines instead.

## 2. The growth problem

The user's addiction grows three stores at different rates and with different
costs. The architecture must keep each on the right path:

| Store | Growth | Size ceiling | Where it costs |
|---|---|---|---|
| **Dictionary** (user + learned words) | Unbounded, ~1-20 words/day for a heavy user. 1 year of daily use: 500-5,000 words, 1-20 aliases each | ~1 MB JSON at 5,000 words / 20k aliases | (a) `correct_with_dictionary` fuzzy pass, (b) `known_words()` set, (c) **`preferred_terms` in the polish prompt** (this is the real one: every word today goes into every prompt) |
| **Packs** (tech/brands/legal/medical/names) | Static per release, downloadable, user-toggled | EW ships 5 packs / 31 KB; realistic Teletype budget 10 packs / 200 KB | Corrector only (lane law) |
| **Profile preferences** (greetings/sign-offs/terms) | Slow, dozens | tiny | Prompt only |

### The two performance traps (and their fixes)

**Trap 1: the fuzzy pass.** `correct_with_dictionary`
(`crates/teletype-core/src/pipeline.rs:391`) builds a `Vec<Entry>` and runs
`edit_distance` per token vs every fuzzy word. That is O(tokens x words).
At 200 words it is invisible; at 20,000 alias entries it is a visible tax on
every dictation.

Fix (EW's shape, `WordCorrector`): **two-pass matching.**
1. **Exact pass (always on):** hash map `normalized(alias) -> word`. O(1) per
   token. This is where learned corrections live and where 95% of hits are.
2. **Fuzzy pass (gated):** only for tokens that missed the exact pass, and
   only against a **candidate shortlist**, not the whole store:
   - shortlist = words/aliases within `max_len - 2 ..= max_len + 2` of the
     token length, pre-grouped by length at load time (bucketed index);
   - distance threshold stays 2 (single words) / 3 (phrases), as today;
   - user words first; pack terms only if no user/builtin candidate matched
     (EW's length-gating / source ordering);
   - hard cap: if the shortlist exceeds N (e.g. 400), skip fuzzy for that
     token (exact matches still apply) and log `fuzzy_shortlist_overflow`.
     A user with 5,000 words whose tokens are near 400 of them is a
     contradiction; exact pass already serves them.

Load cost: building the exact map + length buckets for 20k entries is
sub-millisecond to a few ms in Rust; do it lazily on first dictation and on
any dictionary mutation (generation counter, EW-style).

**Trap 2: the prompt.** `pipeline.rs:186` puts **every** known word into
`PromptContext.preferred_terms`. At 500 words this inflates every polish
prompt by several KB, burns context window, and degrades model focus. EW's
answer is the lane split: pack terms never enter the prompt at all, and the
prompt vocabulary is a curated subset.

Fix: **prompt vocabulary = a bounded, ranked subset.**
- Inclusion: user words + learned words + builtin seeds. **Never pack terms**
  (lane law, see 3.4).
- Ranking: `frequency_used` desc, then `last_used` desc, then manual
  (non-learned) words before learned.
- Budget: first K terms (K = 50 default, setting `prompt_term_budget`),
  hard byte cap 4 KB of term text.
- Learned words with `frequency_used == 0` (learned, never fired) are last in
  the ranking; they still get in until the store exceeds the budget, then
  they are the first evicted. That is fine: if the mishearing recurs, the
  *corrector* (exact pass) handles it deterministically without the prompt.

**Trap 3 (storage): the JSON file.** `JsonStore` rewrites the whole file on
every save. A learned word is at most a few saves per dictation, so rewriting
a 1 MB file is acceptable for years. Decision: **stay on JSON** (atomic
tmp+rename already in place). Migration path if it ever hurts: the store is
one `Vec<DictionaryWord>`; swapping to SQLite or an append-log file behind
`JsonStore`-shaped traits is a contained change. Do not pre-build it.

**Decay (EW has none; we add a light rule):** learned words with
`frequency_used == 0` and `learned_at` older than 90 days are *not* deleted
(privacy: the user may want them back), but the Dictionary screen shows an
"Inactive" filter and a "Clear inactive learned words" action. Deletion is
always user-initiated.

## 3. Build plan

### 3.0 Scope split (matches roadmap numbering)

| Phase | What | Roadmap link |
|---|---|---|
| **Phase 1** | Wire the phrase-level loop (greetings/sign-offs/terms) end to end. This is the existing pi task, unchanged. | T2.1 |

Phases are sequential in dependency but Phase 1 can ship alone.

### 3.1 Phase 1: phrase-level loop (existing task, restate)

As in `tasks/pi-tasks/t21-personalization-loop.md`:

1. `TransformResult.input_text` added (the AI's polished output, for diffing).
2. `record_dictation_edit(ai_output, final_text)` command:
   `extract_signals` -> `apply_signals` on `UserProfile` -> save.
3. Trigger for now: the History screen's "re-edit" flow and a manual
   "Learn from this edit" affordance. No OS-level text watch yet.

**Exit:** repeated greeting/sign-off edits become preferences with
confidence; prompt injection verified.

### 3.2 Phase 2: word-level learning

**Schema (additive, `dictionary.rs`):**

```rust
pub struct DictionaryWord {
    pub id: String,
    pub word: String,                  // canonical spelling (rename-in-mind only; field stays `word` for compat)
    pub pronunciation: String,
    pub created_at: u64,
    pub fuzzy: bool,                   // unchanged: near-miss eligibility
    // --- new, all #[serde(default)] ---
    pub aliases: Vec<String>,          // user-typed sound-alikes
    pub learned_aliases: Vec<String>,  // subset of aliases the app learned
    pub learned_at: Option<u64>,       // Some => word was auto-created
    pub frequency_used: u32,           // corrector hits into this word
    pub last_used: Option<u64>,
    pub category: WordCategory,        // general | person | brand | acronym | domain
}
```

`Dictionary` gains:

- `find_by_alias(normalized) -> Option<&DictionaryWord>` (exact pass)
- `learn(canonical, alias) -> LearnOutcome` with EW's outcome set:
  `Learned { pill: LearnPillModel } | AlreadyCovered | Refused(RefuseReason)`,
  `RefuseReason = TargetGone | AliasOwnedElsewhere | WriteFailed`.
- `undo_learn(pill_id) -> UndoOutcome` with in-memory `UndoRecord { word_id,
  operation: Added | Updated, pre_save: Option<DictionaryWord>, post_save:
  DictionaryWord }` (single active record, EW rule: a new learn replaces it).

**Judge (new `crates/teletype-core/src/personalization/judge.rs`),
deterministic only for now.** Port the `RulesCorrectionJudge` policy (v2)
from EW, which is fully specified in its header comment:

1. Spelled-out acronym ("gee cee pee" -> "GCP") is a correction.
2. Same letters (case/space/punct only) is NOT a correction, except a
   whitespace split joined into an internally-capitalised brand/acronym
   ("dolt hub" -> "DoltHub"); ordinary Title Case never counts.
3. A side with no letters is formatting, not vocabulary.
4. Strip unchanged edge words first; empty residual => insert/delete, not a
   mishearing.
5. Permutations and single function-word insertions are grammar, not
   vocabulary.
6. Closed-class grammar tables (articles, prepositions, auxiliaries,
   pronouns, contractions, irregular paradigms) are not corrections;
   inflection-shaped suffixes on stems >= 4 chars are a heuristic only and
   never override internally-capitalised or acronym-shaped words.
7. Similarity is scored on the RESIDUAL only (Levenshtein + bigram Dice +
   Soundex; Teletype already has `edit_distance` in `pipeline.rs` and can add
   Dice/Soundex in ~50 lines). Every changed word must qualify on its own;
   no mean score.
8. Name-shaped single replacements need less resemblance.

Contract: `judge_correction(original: &str, corrected: &str) ->
Verdict { NotCorrection, Correction, CorrectionAndSafe { alias } }` where the
advisory alias is never read by production (parity with EW).

**Trigger (Teletype-flavoured, no accessibility watch):**

- Primary: History screen. Each history entry stores `raw_input` and
  `final_text` today. When the user edits an entry's text (new
  `update_history_text` command), diff old vs new, run the judge on each
  candidate word swap, save approved corrections via `Dictionary::learn`.
- Secondary: `record_dictation_edit` (Phase 1 command) also runs the judge
  on terminology swaps, so the one command feeds both stores: phrase signals
  -> profile, word corrections -> dictionary.
- Gate: setting `learn_from_edits` (default **on** for History-triggered
  learning; the OS-watch variant never existed here, so no permission
  surface).

**UI (Dictionary screen + pill):**

- After a save: pill "Added \"Saoirse\" to Dictionary" / "\"Saoirse\"
  updated" with **Undo** for 3 s (hover does not extend, EW rule). Phases:
  `learned -> undone (1.5 s) | undo_error (3 s)`. Refusal: "Couldn't save
  \"Saoirse\"" for 3 s.
- Dictionary screen: sparkle on auto-learned words/aliases, "Auto-learned"
  filter, "Inactive" filter (see 2, decay), edit/delete as today. Learned
  aliases render under the word, marked; removing a learned alias is a plain
  delete (no tombstone needed for aliases).

**Tests (mirror EW's suite names, Rust edition):**

- Judge: every policy rule gets a fixture (spelled acronym, case-only,
  brand join, residual-empty, permutation, grammar table, inflection,
  name-shape). EW's `RulesCorrectionJudgeTests` is the fixture source.
- `learn`: new word / existing word / alias-owned-elsewhere / target-gone /
  write-failed; idempotent re-learn returns `AlreadyCovered`.
- `undo`: added / updated / stale / already-changed / failed.
- Corrector: exact alias hit before fuzzy; learned alias fires on next
  dictation (integration: dictation of the mishearing produces the
  canonical).

**Exit criteria:** dictate a name the app mishears, fix it in History, pill
shows, next dictation of the same sound produces the right spelling; undo
restores byte-exactly; no rewording edit ever creates a word.

### 3.3 Phase 3: vocabulary packs

**Format:** read-only JSON resources, EW-compatible shape
`{ "<canonical>": ["alias", ...] }` so a pack file works in both apps.
Location: `crates/teletype-core/assets/packs/<id>.json` (compiled in, zero
download) + optional user-installed packs in
`<config_dir>/packs/` (same format, `id` = filename stem).

**Catalog (Teletype v1, all compiled in):**

| id | Content | Source of terms |
|---|---|---|
| `tech` | frameworks, infra, tooling | curated from public mishearing reports + our own history (opt-in, anonymised) |
| `brands` | company/product names | same |
| `medical` | drug names, conditions | same |
| `legal` | terms of art | same |
| `names` | common given names | same |

Term counts: aim < 500 canonicals per pack (~20-40 KB each). Packs are
**data we author**, not EW's files copied (license/clean-room; the *format*
is compatible, the *contents* are ours).

**Store (`crates/teletype-core/src/packs.rs`):**

- `VocabularyPackStore::load(id) -> Pack { canonical, aliases }`
- `terms_for(enabled: &Set<PackId>) -> Vec<PackTerm>` with deterministic ids
  (EW: `deterministicID(packID, canonical)` so overrides are stable).
- Enabled set in settings (`enabled_packs: Vec<String>`).

**Lane law (the important part, EW's `VocabularyLanes`):**

- Pack terms enter **only** the corrector's exact/fuzzy passes, and only
  **after** user + builtin passes miss (source ordering).
- Pack terms **never** enter `preferred_terms` in the polish prompt.
- Enforcement: the pipeline constructs two distinct values,
  `CorrectorVocabulary { terms, generation }` (builtins + user + enabled
  packs) and `PolishVocabulary { terms, generation }` (builtins + user
  only), and `PromptContext` accepts only the latter. A leak is a compile
  error, not a rule.
- **Overrides:** a user word whose canonical equals a pack term shadows it.
  A learned correction targeting a pack term creates a user override word
  (EW's `packOverride` path); undo removes the override and the pack term
  shows again.

**UI:** Settings > Dictionary > Packs: row per pack (name, description,
term count, enable toggle). No per-term UI for packs (they are not the
user's words); overrides appear in the normal word list tagged "override".

**Exit:** enabling `tech` makes "cheropick" -> "cherrypick" without any user
word; the same term never appears in any polish prompt (golden-string test,
EW's `PackToPolishLeakTest` equivalent).

### 3.4 Phase 4: import/export + scale hardening

**Import/export (P3.9):**

- Export: JSON, user source only (builtins and pack terms excluded, EW
  rule: export filters on `source == .user`). Shape:
  `{ "version": 1, "words": [{ "word", "pronunciation", "aliases",
  "category", "fuzzy" }] }`.
- Import: same shape; case-insensitive dedupe; on conflict the import's
  aliases merge into the existing word (learned provenance only if the
  imported file marks it); report added/merged/skipped counts.
- Both behind `import_dictionary` / `export_dictionary` commands +
  Dictionary screen buttons.

**Scale hardening (the 2-trap fixes from section 2, as work items):**

1. `correct_with_dictionary` rewrite: exact pass via `HashMap<String,
   WordId>` + length-bucket fuzzy shortlist + 400-candidate cap + source
   ordering (user/builtin before pack). Bench fixture: 20k entries, 5k
   tokens, p50 < 1 ms.
2. `preferred_terms` ranking + budget (K=50, 4 KB cap) + setting.
3. `frequency_used` / `last_used` writer in the corrector (bump on hit,
   debounced save: dirty flag, save at most once per 30 s or on app
   suspend, EW's Phase 3b writer shape).
4. Migration: `dictionary.json` v2 -> v3 is automatic (serde defaults);
   round-trip test that an old file decodes and re-encodes with the new
   fields defaulted.

**Exit:** 5,000-word / 20k-alias dictionary: dictation latency delta vs
empty dictionary < 1 ms (bench), prompt size bounded, import/export
round-trips byte-stable.

## 4. Impact analysis

### Performance

| Path | Today | After Phase 2 | After Phase 4 |
|---|---|---|---|
| Corrector, empty dict | 0 | 0 | 0 |
| Corrector, 200 words | ~0.1 ms | ~0.1 ms (exact map lookup) | same |
| Corrector, 5,000 words / 20k aliases | would be ~5-20 ms (O(n) fuzzy) | ~1-3 ms (fuzzy still O(n) but rare) | < 1 ms (bucketed shortlist) |
| Polish prompt size | grows unbounded with words | same (prompt fix is Phase 4) | bounded: 50 terms / 4 KB |
| `dictionary.json` at 5,000 words | - | ~1 MB, rewrite per save, fine | same; SQLite only if measured bad |

### Memory

- In-memory: exact map + buckets for 20k entries ~ a few MB worst case.
  Negligible vs the ASR/LLM footprint.
- No new process, no new model (the judge is pure Rust; the EW CoreML model
  arm is explicitly deferred and on-demand if ever added).

### Binary size

- Judge + packs + stores: < 200 KB. Packs add ~100-200 KB compiled in.
  Well inside the 13 MB budget; note it in `THIRD-PARTY-NOTICES` only if
  pack data ever comes from a third party (v1 data is self-authored).

### Privacy

- Everything local: watched/diffed text, learned words, pack terms never
  leave the machine (non-negotiable).
- One honest caveat to surface in UI copy (EW states the same one): custom
  words are sent to the *user's chosen* cloud polish provider along with the
  text, under the user's own key. Pack terms are not (lane law).
- No telemetry (non-negotiable): EW's `learn_*` events become local log
  lines in the existing log screen.
- Learned words are the user's data: exportable (Phase 4), deletable,
  filterable; "Clear inactive learned words" is the only bulk action and it
  is explicit.

### UX surface

- Dictionary screen: +sparkle, +2 filters, +packs section, +import/export.
- Pill: +learned-correction variant with 3 s undo.
- History screen: edits become a learning trigger (no new UI, existing edit
  flow).
- Settings: +`learn_from_edits` toggle, +`prompt_term_budget`.

### Risk

| Risk | Mitigation |
|---|---|
| Judge misclassifies a rewording as a correction | Deterministic rules are conservative by design (EW iterated v1 -> v2 after failing its frozen report); save-at-once + 3 s undo + Auto-learned filter + explicit delete bounds the blast radius |
| Alias collision (a mishearing already owned by another word) | `AliasOwnedElsewhere` refusal, typed, surfaced in the error pill (EW rule) |
| Learned-word pollution of the prompt | Lane law (compile-time) + budget/ranking (Phase 4) |
| JSON store too slow at extreme scale | Measured in Phase 4 bench; migration path is one trait swap, decided on data, not fear |
| Pack data provenance | Self-authored v1; format-compatible with EW for user interchange, contents not copied |
| Undo window race (user edits the word mid-window) | `already_changed` outcome: nothing written, pill says "Couldn't undo" only on write failure, silent close on already-changed (EW rule) |

### What this plan does NOT do

- No OS-level text watch of the pasted document (the big EW piece; revisit
  only if History-triggered learning proves under-used).
- No CoreML/ONNX judge model (revisit with a measured need; would be
  on-demand download with checksums like the other models).
- No per-word UI for pack terms.
- No cross-device sync of the dictionary (out of product scope today).
