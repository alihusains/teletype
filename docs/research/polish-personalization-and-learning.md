# Polish, personalization, and vocabulary learning: product research

Date: 2026-10-10
Scope: First-party Wispr Flow documentation and direct Teletype/EW source inspection. This is behavioral research, not a claim that private Wispr internals are known.

## What Wispr publicly documents

- **Styles are selected by writing context.** Wispr documents Personal messages, Work messages, Email, and Other contexts, with presets including Formal, Casual, Very casual, and (for some categories) Excited. Their examples vary capitalization, punctuation, and tone by context. Source: [Flow Styles setup](https://docs.wisprflow.ai/articles/2368263928-how-to-setup-flow-styles).
- **Polish is an editable transform, not merely punctuation cleanup.** Wispr documents clarity/concision, reordering and adding structure, maintaining tone, custom rules, and applying transforms to selected/readable text. It also describes reviewing changes and retry/undo. Sources: [Transforms beta](https://docs.wisprflow.ai/articles/8068950331-how-to-use-transforms-beta), [custom Polish rules and shortcuts](https://docs.wisprflow.ai/articles/2719941210-how-to-configure-polish-shortcuts-and-custom-prompts).
- **Dictionary learning is user-correctable.** Wispr documents personal vocabulary for names, technical terms, acronyms and other terms, with the ability to review/edit/remove words and corrections. Source: [Teach Flow your words](https://docs.wisprflow.ai/articles/4052411709-teach-flow-your-words-with-the-dictionary).
- **Insights expose value and corrections.** Wispr documents usage stats, dictation speed, words, streaks, and correction categories. Source: [Usage tab](https://docs.wisprflow.ai/articles/8760230576-your-usage-tab-track-your-dictation-stats-in-wispr-flow).
- **Context awareness has privacy and reliability bounds.** Public docs say the desktop app can use focused-field/selection and app context, may skip sensitive fields, and behavior varies by application/platform. Source: [Feature context awareness](https://docs.wisprflow.ai/articles/4678293671-feature-context-awareness).
- **Personalization setup is staged and saves selections in place.** Wispr's current desktop style setup walks through Personal messages → Work messages → Email → Other, then permits changing a category directly. Current desktop guidance states style formatting is English-only. The current documented style distribution is Formal and Casual for every category, Very casual only for Personal, and Excited for Work/Email/Other. This is more nuanced than the older screenshot examples. Source: [Flow Styles setup](https://docs.wisprflow.ai/articles/2368263928-how-to-setup-flow-styles).
- **Context categorization operates at the app/site level and reads nearby text.** Wispr says it recognizes the active app or website, reads text near the cursor and may use visible recipients/names; its own docs describe exclusions for password/sensitive/numeric fields, URL bars, banking/financial apps, and its own app. The docs also say context is cleared at dictation end and that reading is skipped if it cannot finish quickly. Source: [Feature context awareness](https://docs.wisprflow.ai/articles/4678293671-feature-context-awareness).
- **Transforms are discoverable and recoverable.** Wispr documents keyboard activation on selected text, a review/diff surface, retry from the original, and undo. Its desktop docs warn that URLs/links and nested list formatting can change. Source: [Transforms beta](https://docs.wisprflow.ai/articles/8068950331-how-to-use-transforms-beta).
- **Vocabulary learning uses explicit user corrections and filters noise.** Wispr's docs list candidate classes and exclusions such as file paths, domains, IDs, dates, common names and ordinary acronyms. This is evidence for a conservative suggestion system, not for auto-adding every capitalized token. Source: [Teach Flow your words](https://docs.wisprflow.ai/articles/4052411709-teach-flow-your-words-with-the-dictionary).
- **Keyboard shortcuts are editable and cancellable.** Wispr documents a Change control, recorded bindings, Escape cancellation, duplicate/reserved-key rejection, and limits per action. Source: [Customize keyboard and mouse shortcuts](https://docs.wisprflow.ai/articles/2612050838-supported-unsupported-keyboard-hotkey-shortcuts).

## What Teletype currently has (verified in source)

- `StyleProfileStore` has global profile selection and per-app overrides, but the built-ins are Concise, Professional, and Casual; there is no separate Personal/Work/Email/Other preset choice model.
- AI Polish already supports prompt rules and user instructions, plus a semantic validator that protects meaning and identity-sensitive values. Selection transforms exist.
- Personalization packets can include learned style/term preferences. A dictation correction can learn terminology into the dictionary, but source flow is correction-driven; the first successful standalone Polish result does not expose a candidate-word approval list.
- Edit observation is deferred until the next dictation (with a 15-minute freshness window) because applications do not expose a reliable field-edit event. The watcher only learns when the same app remains frontmost and the field remains readable; it offers an undo toast when a preference is learned. `learn.rs::apply_signals` currently deduplicates learned preferences by description without scope, so identical signals across categories can retain the first category's scope. This is a concrete issue to fix before category-scoped personalization is trusted.
- Dictionary entries have learned provenance; the UI has a generic learned indicator. The Quick Add shortcut currently inserts a selected token directly and only logs errors, rather than presenting a user review/undo affordance.
- Insights expose dictionary/learned word totals and a Polish availability status, but not Polish usage/review counts or Polish-origin learning counts.

## Product recommendations for Teletype

1. Offer the four context tabs and the three requested presets (Formal, Casual, Very casual) as actual per-context preferences. Keep the style controls independent from transform rules; combining them at prompt assembly avoids duplicating presets as separate transforms.
2. Use explicit context categories derived from safe app classification or user choice. Do not inspect arbitrary screen contents by default. If selection/context is available for a user-invoked transform, explain the scope and keep the original text recoverable. A future opt-in focused-field context feature needs per-field safety exclusions, a strict latency budget, and in-memory lifecycle cleanup.
3. Make the Polish instruction explicit: preserve facts, names, numbers, links, intent, and voice; fix spelling/grammar; improve clarity and structure only as needed. Avoid adding claims or changing commitments. Let users inspect and undo the result.
4. Surface candidate vocabulary from polished output as suggestions, never automatic dictionary writes. Filter existing entries and ordinary words; require explicit Add. Store a provenance/source and timestamp so “Learned by Teletype” is honest and removable.
5. Keep Polish Insights local and aggregate-only: runs, accepted/reverted outcomes where observable, and vocabulary suggestions accepted. Avoid storing text or sending analytics.
6. Make Polish low-friction: shortcut visible as editable keycaps, fast selection transform, useful examples, retry and undo, and suggestions that can be dismissed without blocking the edit. Save style picks immediately and let the user choose one category at a time; make the active context and selection easy to understand.

## Limitations

Wispr's docs describe user-visible behavior, not its private ranking algorithms, model prompts, training, or exact context pipeline. Recommendations above are product inferences based on those documented behaviors plus Teletype source inspection. No Wispr implementation internals were inspected.
